## Findings

### F-001 — Absorb decision applied against a buffer that may have changed since classification
- **Severity:** HIGH
- **Status:** RESOLVED (verification pass) — BR-19 + DC-21 genuinely close the failure mode. Re-derivation occurs against the *live* buffer at the instant of application: a clean-at-read buffer that turned dirty does not run the clean absorb path (DC-21 bullet 1); the re-evaluation re-runs the equality gate (DC-11) → silent absorb only if content-identical, else collision sheet, so a typed character is always preserved or surfaced (BR-19.2). Adjacent-gap attack (same lens): no livelock — DC-21 re-derives once against the held settled disk content, it does not loop a fresh coordinated read; no path drops a real external change — a divergent change becomes a collision (surfaced), never silently swallowed; no spurious sheet on the unchanged-buffer common case (BR-19.4 / DC-21 bullet 4). Fix holds with no introduced gap.
- **Lens:** failure modes / integrity
- **Trace:** feature declaration "Spurious prompts … treated as a defect" and its inverse — the feature must "never silently overwrite the user's work"; BR-1.1, BR-1.5 (absorb without losing edits/mode), BR-2.3 (buffer/cursor preserved).
- **Finding:** DC-19/§Concurrency state that coordinated reads run off the main actor and are "hopped back to the main actor before touching the buffer." The detector classifies `absorb` from the buffer state *as sampled during that off-main read* (clean buffer → absorb, DC-12). Nothing in the design requires re-checking the buffer at the moment the absorb is applied on the main actor. Sequence: buffer is clean → external change arrives → detector begins coordinated read → user types one character → read completes → detector hops to main and adopts disk content + resets last-known-disk (DC-12). The just-typed edits are silently overwritten, with no sheet, because the collision check was made against a stale (clean) snapshot. This is precisely the "silently drop user edits" failure the feature exists to prevent, and it fires in normal single-device editing where a real external change coincides with active typing — not an exotic case.
- **Recommended action (architecture):** Add a DC stating that the absorb/collision classification is re-validated against the current buffer on the main actor immediately before any buffer mutation: if the buffer changed since the read snapshot, the outcome is re-derived (a buffer that became dirty re-runs the equality gate → collision or a fresh coordinated read), and absorb never adopts disk over edits made during the read. Make this an observable property anchored to BR-1.1/BR-2.3.

### F-002 — Autosave write can clobber disagreeing disk content in the gap between `collision` classification and sheet presentation
- **Severity:** HIGH
- **Status:** addressed (verification pass: NOT promoted to resolved). The classify→present clobber window is genuinely closed for the foreground case: BR-20 + DC-22 (tightening DC-14/DC-16) suspend save-back from the classification instant and cover the queued/idle-debounced save in the gap (BR-20.2) and the deletion-recreate gap (BR-20.3). However, attacking the fix with the original lens surfaced an adjacent gap introduced by re-keying suspension to the latched outcome (lifts "only on explicit resolution"): if the system dismisses the sheet/banner during backgrounding, suspension never lifts and the detector stays quiescent, with no re-present or re-arm path — see new finding F-003. Left addressed (not resolved) until F-003 is closed.
- **Lens:** failure modes / integrity
- **Trace:** BR-4.3 ("no resolution happens without the user's tap"; the open document is not silently overwritten by either side while the choice is pending); declaration "user is the only authority."
- **Finding:** DC-14 suspends the save bridge's autosave "while [the sheet] is up." But the detector emits `collision` from an off-main read and the sheet is presented later on the main actor. The save bridge runs on a 500ms idle debounce (inherited architecture). In the window between the detector deciding `collision` and the sheet actually being presented (off-main read latency + main-actor hop + SwiftUI presentation), a queued autosave can fire and write the user's dirty buffer to disk, clobbering the disagreeing external content that the collision was about — before the user ever sees Keep Theirs. The pending external content is then lost, and a Keep-Theirs/Discard-Mine choice can no longer recover it. The suspension must begin at *classification*, not at *presentation*.
- **Recommended action (architecture):** Specify that autosave suspension for the document begins the instant the detector classifies `collision` (and `deleted`), not when the surface is presented — i.e., suspension is keyed to the outcome being latched, closing the present-the-sheet latency gap. Anchor to BR-4.3 / BR-9.3.

### F-003 — Classification-keyed suspension never lifts if the system dismisses the surface (stuck-suspended state)
- **Severity:** HIGH
- **Status:** addressed (requirements portion); architecture mechanism pending — BR-21 fixes the behavior (a non-user dismissal never marks a collision/deletion resolved; the unresolved state and its suspension are preserved and, on foreground return, re-presented or recoverably lifted, so suspension can never outlive the surface indefinitely). The design mechanism (the foreground re-validate-and-re-present/lift path, the recoverable lift condition replacing DC-22's "only on explicit resolution," and the tightening of DC-22 bullet 4 / DC-15) is pending in design.md.
- **Lens:** failure modes / integrity (adjacent gap introduced by the F-002 fix)
- **Trace:** BR-15 ("on return the user can still complete the choice, **or** the buffer is preserved if the sheet was dismissed by the system"); BR-20.4 / DC-22 ("suspension lifts only on explicit resolution"); DC-5 (detector quiescent until the user resolves); DC-15. Declaration "user is the only authority" and "never silently lose the user's work."
- **Finding:** F-002's fix re-keys autosave/save-back suspension to the *latched classified outcome* rather than to surface presence, and DC-22 bullet 4 states it "lifts **only** on explicit resolution." DC-15 / BR-15 explicitly contemplate the branch where the system (backgrounding, memory pressure) dismisses the sheet or banner — promising only that the buffer is preserved in memory; neither specifies any mechanism to **re-present** the surface or **re-arm** the gate. Result: surface gone + outcome never user-resolved → suspension is permanent and the detector (DC-5) stays quiescent indefinitely. The user's edits silently never persist and no further collision/deletion ever surfaces — a silent data-at-risk state that contradicts the protection the feature exists to provide. Note the regression direction: the *prior* "while the sheet is up" scoping (old DC-14/DC-16) implicitly resumed autosave when the system tore the sheet down; the F-002 fix removed that implicit resume without replacing it with an explicit re-present-or-resume path. So the fix that closed the present-latency clobber opened a stuck-suspended path on system dismissal.
- **Recommended action (architecture):** Add a DC making suspension and detector-quiescence recoverable when the surface is dismissed without an explicit user resolution: on foreground/return, if a `collision`/`deleted` outcome is latched but its surface is no longer presented, the detector re-validates against the current settled disk + live buffer (reusing DC-21) and either re-presents the surface or — if the outcome no longer holds — lifts suspension and resumes normal operation. Define the lift condition behaviorally (not "only on explicit resolution") so suspension can never outlive the surface indefinitely. Anchor to BR-15 / BR-20.4, and make it an observable property: background with a sheet pending, let the system dismiss it, return → either the sheet is back or autosave/detector are demonstrably live again, never frozen.
